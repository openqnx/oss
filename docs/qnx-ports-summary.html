Defects found — and only findable by running the code

Every one of these produced a library that compiled and linked without complaint. Building is not evidence; these surfaced on a real target, under gdb, or in a from-scratch rebuild.

WebKitGTK ports; a browser window does notEGLNativeDisplayType

The engine builds and runs on QNX and reports itself as Mozilla/5.0 (X11; QNX RaspberryPi5) AppleWebKit/605.1.15. Seven fixes were needed and only two were about QNX — CMake 4's stricter if(), ICU 76's second C++ API switch, and a PID-socket argument GLib ports push unconditionally while guarding its declaration, its fd hand-off and the child's parsing with OS(LINUX), are upstream problems any current build hits. What is genuinely QNX: its only EGL belongs to Screen and types EGLNativeDisplayType as an integer handle, so WebKit's X11 and Wayland display backends do not compile. Turning both off costs 2 of 1712 source files; painting into a window would need a PlatformDisplay backend written against QNX Screen, which is new development, not a port.

56 libraries linked QNX's prebuilt libintl--disable-nls

gettext was configured without NLS, so it installed no libintl at all — and glib, GTK, ATK and every Xfce component quietly resolved -lintl to the SDP's libintl.so.1. The audit could not see it: it only flagged sonames whose stem we had also staged, and a library we never installed has no stem to match. It now works from an explicit allowlist of genuine OS and toolchain libraries, and reports everything else. Under that rule the whole tree had exactly one offender.

JavaScriptCore aborted before running a linestructure heap

JSC reserves its structure heap aligned to 4 GB; the size halves on failure but the alignment does not, so every attempt needs up to 8 GB of address space. A 1 GB QNX VM cannot give that and the RELEASE_ASSERT fires inside JSContextGroupCreate(). It passed on an 8 GB Raspberry Pi, so it read as an architecture difference and was really an address-space one. Found by taking a core with QNX's dumper and reading it with the SDP's cross gdb.

The clean rebuild found six more218 packages, one pass

Rebuilding the whole tree from nothing turned up four undeclared dependencies — one of which (aspell) was linking QNX's prebuilt ncurses — two patches that existed only as edits in src/ and would have been lost, and a package whose feature detection had silently changed underneath it. Every one of them built fine incrementally. The run also broke itself: env.sh prepends to PATH on each of its two sourcings per package, and at 218 packages PATH crossed the kernel's 128 KB limit, after which every exec failed with "Argument list too long" — starting with the dirname that locates the workspace.

test_python was testing QNX's Python/system/lib/python3.14

With an isolated config and no program name, CPython finds its prefix by searching PATH for python3. On the Pi that is QNX's own interpreter, so our libpython loaded QNX's stdlib and its prebuilt _ssl, _ctypes and _sqlite3 — and the test's ssl, sqlite3 and libffi-callback checks never touched our ports. The x86_64 image has no system Python, which is how it surfaced. The bundle now carries our stdlib and the test asserts every module loads from inside it.

LuaJIT crashed on print(1)buildvm host layout

LuaJIT generates its interpreter by running buildvm on the build machine, and for a target its Makefile does not list it compiles buildvm as LUAJIT_OS_OTHER while the target code sees POSIX. Those disagree on LJ_HASPROFILE, which changes the size of jit_State — and the VM finds global state by offsets from the dispatch table that follows it. Every such access was 16 bytes off. It built, linked and passed every static audit; gdb on the Pi showed a lua_State with odd base/top addresses. The recipe had described this mismatch as harmless.

Two protobufs and two abseils in one processgRPC PROVIDER=module

gRPC installed its bundled protobuf 29.0 and abseil 20240722 beside the protobuf recipe's 29.3 and abseil 20240116 — 89 libraries twice, headers merged file by file, and c-ares's libcares.pc overwritten. The gRPC test mapped both pairs and still passed. One abseil recipe now, providers switched to package, and a new check-dupes audit.

cairo's Xlib surface needs SysV shm<sys/shm.h>

QNX 8.0 has no System V shared memory at all, so X11's MIT-SHM is impossible there. cairo already had a no-SHM path; it is now taken when the header is absent.

VTE could not open a pty at allTIOCPKT

QNX's <sys/ioctl.h> defines TIOCPKT — commented "pty: set/clear packet mode" — but devc-pty does not implement it and returns ENOTTY, so vte_pty_new_sync() failed outright. Ignoring the errno would have been worse than the failure: vte.cc's reader is compiled under the same #if and strips a leading packet-header byte from every read(), so the first byte of real output would have been eaten and misread as a header. A compile-time probe for a request the kernel may not honour has to switch every site that depends on it, together.

A staged target binary broke every later CMake buildpkgconf

Porting pkgconf put a QNX binary in stage/<arch>/usr/local/bin, which sits on CMAKE_PREFIX_PATH. find_package(PkgConfig) matched it, tried to run it for a version, and reported "Could NOT find PkgConfig" — naming neither the file it found nor why it rejected it. Staging's bin and sbin are now in CMAKE_IGNORE_PATH.

at-spi2-core silently replaced ATKlibatk-1.0.so.0

ATK moved into at-spi2-core upstream at 2.52, so 2.54 installs its own copy. With the standalone atk recipe still present, both staged a libatk-1.0.so.0.* and build order picked the winner — the ordering dependence a clean rebuild exists to eliminate. Nothing failed at build time; it surfaced on target, because 2.54 aliases ATK_ROLE_PUSH_BUTTON to ATK_ROLE_BUTTON and atk_role_get_name() changed its answer.

enchant found none of its own pluginsgnulib relocate()

gnulib's relocatable.c locates the running shared library by reading /proc/self/maps — implemented for Linux and Cygwin, and for nothing else. On QNX the function compiles away, relocate() becomes the identity, and enchant kept composing its provider directory from the configure-time prefix. The broker constructed cleanly and enumerated zero providers anywhere but that one path, with no error at any layer. dladdr() asks exactly the question the /proc scan asks, and QNX has it in libc. Any package vendoring this gnulib module carries the same hole.

ThorVG shipped a library with no symbolsTVG_STATIC

Meson's --default-library=both makes ThorVG define TVG_STATIC, and TVG_STATIC expands its TVG_API visibility macro to nothing. The shared object compiled, linked and installed exporting zero tvg_* symbols. Building a shared-only library restored 121. Any project whose visibility macro keys off a static-build define behaves this way, and nothing short of linking against it says so — check-devlinks now flags a staged .so with an empty dynamic symbol table.

Build driver clobbered recipesscripts/qnxbuild

Recipe variables and hook functions cannot be local in bash, so a package that recursed to build a dependency came back holding the dependency's recipe — then installed with it and stamped itself done. glib stamped "OK" while staging no glib at all. Invisible until a clean rebuild made recursion the normal path: every earlier build had depended on lucky ordering.

libffi handed out non-executable closuresFFI_MMAP_EXEC_WRIT

The executable-memory allocator is gated on __linux__ or Windows; everywhere else libffi falls back to malloc. On QNX every closure call jumped into the malloc arena — gdb put rip at __main_arena+2240. That breaks every libffi callback, which is the mechanism behind Python ctypes and all GObject introspection.

SDP prebuilt libraries linked silentlycheck-sdp-leak

The QNX gcc spec injects its own -rpath-link with four SDP directories ahead of anything you pass, and find_package() searched the SDP first. Eleven libraries were shadowed; binaries recorded libz.so.2 (the SDP's soname) instead of our libz.so.1 and loaded QNX's copy on target — precisely what the brief forbids.

Orc registered no compile targetaarch64 only

ARM NEON detection reads /proc/cpuinfo, which QNX does not have, so the backend was marked non-executable and every Orc program fell back to the interpreter — silently losing the SIMD fast paths in GStreamer's converters. x86_64 passed; only the Raspberry Pi run caught it.

readline installed no development symlinklibreadline.so

support/shlib-install has no case for nto-qnx, so only libreadline.so.8 was staged. -lreadline is then not an error: the linker keeps searching and finds the SDP's prebuilt copy.

Shared libraries shipped with holeslibyuv, libSvtAv1Enc

Shared libraries link with undefined symbols allowed, so a forgotten target_link_libraries installs cleanly and fails only when an executable finally links it. libyuv compiled its MJPEG decoder but linked libjpeg into a tool alone; SVT-AV1 referenced cpuinfo_isa from a cpuinfo build that excluded QNX.

CommonAPI aborted at process exitmutex lock: EINVAL

A use-after-free across DSO finaliser order: libCommonAPI destroyed the Runtime singleton whose member mutex libCommonAPI-SomeIP then locked. glibc tolerates the stale mutex; QNX returns EINVAL, libc++ throws, the process aborts. Root-caused with a gdb backtrace on target.

CPython built a static library while reporting success--enable-shared

Three platform tables omit QNX, so --enable-shared was accepted and quietly produced libpython3.14.a. Its existing QNX case for LINKCC was written for native builds and dropped qcc's -V target selector, so the cross build drove the x86_64 linker against aarch64 objects.

Not built — and why

These are blocked on something structural, not on time.

zenoh-c · Kuksa

Rust. No toolchain on this host, and stock rustup ships no QNX 8.0 std target — the qnx-ports/rust bootstrap has to come first.

can-utils

Not a port. Every tool is written against SocketCAN (AF_CAN/PF_CAN), which QNX does not have — it uses dev/can resource managers. A translation layer would have to be written first, which is new development.

Weston

Hard-requires libinput and libdrm at configure time even for the headless backend. libinput needs udev, libevdev and mtdev — the Linux device model. GTK3's widget layer is covered through Broadway instead.
